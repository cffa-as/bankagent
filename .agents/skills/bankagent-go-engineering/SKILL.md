# bankagent Go 后端工程规范

## 适用范围

修改 Go API、领域服务、Agent 编排、权限策略、动作状态机、Mock 银行账本、SQLite 仓储、审计或相关测试时使用。当前仓库处于方案评审阶段；没有已确认的调用方和验收标准前，不提前实现业务代码。

## 编码约束

- 提交前运行 `gofmt`；命名遵循 Go 惯例，优先短而清楚的局部变量和小函数。
- 错误要被处理或向上返回；需要补充上下文时使用 `%w`，不要吞错、用字符串比较错误或把业务失败伪装成成功。
- 使用 `context.Context` 传递取消、超时和请求范围；不要把 context 存进长期对象，也不要用固定 `time.Sleep` 证明并发顺序。
- HTTP 边界统一解析和校验请求；内部函数基于已校验的类型工作，避免多层重复防御。工具参数必须经过 Schema/类型校验并限制在服务端白名单内。
- API、领域规则、仓储和外部工具保持清晰分层；没有真实调用方、复用或测试收益时，不新增接口、包装层、兼容层或配置项。
- 金额使用整数最小货币单位，不使用浮点数；幂等键、动作状态、风险等级和审计事件使用集中定义的常量或类型。

## 银行场景硬约束

- 模型输出只代表意图、实体和候选计划，不代表授权、风险判断或执行结果。
- 风险计算、确认/MFA、动作快照、取消/过期、执行门、幂等和账户状态由 Go 服务端确定性处理。
- 确认、取消和副作用启动必须位于可竞争的事务或原子状态转换边界；重复确认只能产生一次副作用。
- SQLite 写操作使用明确事务；唯一约束用于幂等和关键业务不变量。不能把 SQLite 内存替身的通过结果当作生产数据库并发语义证明。
- 业务成功只能来自 Mock 银行工具的结构化回执；日志、Trace 和审计必须脱敏，不记录密码、验证码、Token、完整账户号或真实个人信息。

## 测试与验证

- 风险阈值、金额计算、Schema、状态机、MFA 和幂等规则优先使用表驱动单测；单测零外部网络、秒级完成。
- HTTP、SQLite 事务、工具网关和主链路使用集成测试；E2E 只验证跨边界契约，不复制内部规则。
- 并发测试用锁、事务、channel、barrier、WaitGroup 或可控 fake 建立 happens-before，不用固定 sleep。
- 涉及并发的改动运行受影响包的 `go test -race`；提交前至少运行受影响包的 `go test` 和 `go vet`，并在交付说明中区分已执行与未执行的检查。
