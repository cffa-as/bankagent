# bankagent 设计规范

## 使用时机

以下任一情况必须使用本 skill：

- 新增或调整用户场景、功能、页面或交互。
- 修改权限等级、确认/MFA、动作状态机、幂等或审计。
- 新增 API、数据库表、核心数据结构或跨模块流程。
- 评审产品需求、概要设计、架构方案或安全边界。

## 先判断范围

开始写文档前，先回答：

1. 这是六场景首期能力，还是后续能力？
2. 是否产生资金、身份、敏感数据或外部副作用？
3. 是否改变公开 API、数据结构、权限或状态流转？
4. 是否已有文档、接口或模型可以复用？
5. 这项设计是否必须现在存在？

不确定的决策写成“待确认”，不要伪装成已实现或已批准。

## 产品需求文档必须包含

产品需求文档使用 `docs/产品需求.md`，至少包括：

1. 背景与目标
2. 用户与场景
3. 需求范围
4. 功能清单
5. 业务流程
6. 页面与交互

每个功能必须有用户故事、前置条件、主流程、异常流程和可观察的验收标准。涉及高风险动作时，必须写明风险等级、用户确认/MFA、取消、过期和失败后的账户状态。

## 概要设计文档必须包含

概要设计使用 `docs/概要设计.md`，至少包括：

1. 需求背景（用户故事）
2. 总体设计概述
3. 关键数据结构
4. API 协议
5. 数据库变更
6. 关键业务流程说明（结合数据结构与代码接口）

API、数据结构和流程必须保持一致。每个副作用流程至少说明：动作创建、风险计算、确认/MFA、执行门、工具回执、审计、取消/过期和幂等处理。

## bankagent 的设计硬约束

- LLM 只能返回 Schema 约束的意图、实体和候选计划。
- 风险等级和授权状态由服务端确定性计算。
- 关键字段进入动作快照后不可静默修改。
- 成功结果只能来自业务工具回执。
- 用户输入不能创建工具、提升权限或跳过验证。
- 不为首期没有的外部接入、任意代码执行或复杂平台能力预留空抽象。

## 设计评审清单

- [ ] 首期/后续范围明确
- [ ] 用户故事和验收标准可复现
- [ ] 页面行为与 API 行为一致
- [ ] 数据结构覆盖状态、幂等键和审计关联
- [ ] 权限、确认、MFA 和过期条件明确
- [ ] 取消、失败、重试和并发竞争有定义
- [ ] 业务成功有工具回执，不依赖模型自述
- [ ] 敏感数据、日志和 Trace 处理明确
- [ ] 没有无调用方的抽象、配置或未来占位功能

## API 设计约束

- 对外 HTTP 路径统一使用 `/v1` 前缀；资源名使用小写复数和明确的资源 ID。
- 查询使用 `GET`，创建使用 `POST`，局部更新使用 `PATCH`；确认、MFA、取消等状态迁移使用明确的动作子资源。
- 副作用请求必须支持 `Idempotency-Key`；重复请求返回原动作状态或原结果，不重复产生业务副作用。
- 响应统一包含 `trace_id`；错误至少包含稳定的 `error.code` 和面向用户的 `error.message`。
- API 权限、会话归属和动作归属由服务端校验，不能依赖前端路径或模型输出。

## 数据库选择约束

- 评审阶段优先选择满足当前部署规模的最小数据库；首期单实例运行使用 SQLite、事务、WAL 和唯一约束。
- 只有多实例并发写入、高可用或容量指标证明 SQLite 不足时，才引入 MySQL；迁移前先补数据访问边界和数据库集成测试。
