# bankagent 架构自评审（评审稿）

> 日期：2026-10-31
> 结论：方向合理，关键契约已修正，可进入实现前评审。

## 1. 评审范围

本次检查了产品需求、技术方案、概要设计、OpenAPI、仓库协作规范，以及本机 xrobotd 的 Manager API、Session/Turn、工具目录和 Trace 设计。外部参考包括 Revolut AIR、OpenClaw、LangGraph、OpenAI Agents SDK、MCP 和 Temporal 的公开资料。

评审重点是：模型是否可能越权，副作用是否可重复，工具超时后是否能证明账户状态，SQLite 事务边界是否清楚，六个场景是否共用一套安全内核。

## 2. 结论

总体架构可以作为比赛实现基线：Go 服务端掌握策略、授权、动作状态、执行门、账本事务和最终结果；模型只做意图理解和候选计划；MCP 只做受控工具协议；六个场景复用 Action、Authorization、ToolReceipt 和 AuditEvent。

本轮已落实以下原评审问题：

1. 工具调用结果未知进入 `reconciliation_required`，资金工具不自动重试。
2. 幂等记录独立建模，唯一键为 `user_id + method + path + key`。
3. 红色动作创建后进入 `awaiting_mfa`，黄色动作才调用确认接口。
4. 理财申购使用 `product_id`，赎回使用 `holding_id`；MFA 锁定限定在当前 Action；HTTP 错误映射和 MCP 传输、认证、超时规则已固定。

## 3. 已确认的成熟设计

- API 有明确 `/v1` 版本前缀、资源路径、统一响应和 OpenAPI 契约。
- 查询、黄色动作、红色动作分级，且确认/MFA/取消走服务端状态机。
- 快照、幂等、工具回执和审计分开建模，避免模型自述成为业务结果。
- MCP 没有被放进授权内核，模型不能直接调用资金执行工具。
- SQLite + WAL + 事务适合单实例 Mock 账本，暂时不需要为了“看起来像生产”引入 MySQL。
- xrobotd 的 Session/Turn、Trace、工具 Schema、取消和单一仲裁入口适合复用为设计原则，不应复制设备、语音和 Manager 拓扑。

## 4. 实现前的 P1 约束

### 4.1 执行恢复

每次工具调用生成服务端 `tool_request_id`，记录在 `execution_attempts`。调用前后分别写审计；连接断开、超时或只收到 `processing` 时，Action 进入 `reconciliation_required`。后台只按 `tool_request_id` 查询结果，查询不到时转人工接管；没有确认前不得重新扣账。

### 4.2 幂等保存

`idempotency_records` 保存用户、方法、路径、键、请求指纹、响应状态、响应正文、Trace ID 和过期时间。重复请求返回原响应；同键不同指纹返回 `IDEMPOTENCY_CONFLICT`。清理过期记录前必须保留业务动作和审计记录。

### 4.3 工作流恢复

WorkflowNode 的状态必须落库。进程重启后由有限后台 worker 扫描 `ready/running/reconciliation_required` 节点；节点执行前再次检查 Action 状态和依赖，不能靠进程内 goroutine 保存唯一进度。

### 4.4 MCP 网关

MCP 只负责工具发现、参数 Schema 和调用适配。首期默认进程内 Go Gateway，跨进程使用 Streamable HTTP；Gateway 到工具服务使用服务端内部 Bearer Token。只读、Mock 副作用、对账查询超时分别为 5 秒、10 秒、5 秒，资金工具不自动重试；超时或回执未知进入 `reconciliation_required`。Gateway 固定工具白名单、注入用户和 Trace 上下文、限制返回体大小、记录工具版本，并把工具请求 ID 与 Action 绑定。禁止模型自行选择执行权限、账户 ID、幂等键或内部连接。

### 4.5 审计顺序

审计事件增加单调递增 `sequence`，至少覆盖计划校验、策略结果、授权、执行门、工具请求、工具回执、最终状态和对账结果。审计只保存脱敏摘要，不能保存验证码、Token、完整账户号或完整提示词。

## 5. 参考项目后的取舍

| 项目 | 借鉴 | 不复制 |
| --- | --- | --- |
| xrobotd | Session/Turn、工具 Schema、Trace、取消、单一仲裁入口 | 设备、语音、WebSocket、Manager 服务拓扑 |
| Revolut AIR | 单一对话入口连接多个金融能力；敏感动作需要用户批准 | 未公开的内部风控、模型和交易实现 |
| OpenClaw | 运行控制面、会话隔离、审批和人工接管 | 把审计日志当作授权或银行回执 |
| LangGraph / Temporal | 持久化运行、暂停恢复、人工介入、重试和对账 | 首期不引入 Python 运行时或完整工作流平台 |
| MCP | 工具 Schema 和跨进程适配 | 把 MCP 当作权限系统或资金事务系统 |

## 6. 实现顺序

1. 先实现状态机、幂等记录、执行尝试和 SQLite 事务边界。
2. 再实现 Mock 账本和转账闭环，补齐重复请求、取消竞争、超时对账和余额不足测试。
3. 复用安全内核接入理财、卡片、订阅和工作流。
4. 最后接入 MCP 适配和对话模型；模型输出必须始终经过 Schema、Plan Guard 和 Policy Engine。

实现阶段仍需先完成状态机、幂等、MFA 锁定、结果未知对账和工具边界的负向测试，再进入六场景页面联调。
